# Keep unfinished preparation work until deliberate discard

Data preparation now asks before closing or switching studies when recipe, preview, redo history, naming or editor choices would be lost. Keep editing preserves those choices in the mounted tool. Escape opens the question when work is unsaved; Escape within the question returns to editing. Underlying controls are hidden and inert while choosing, and keyboard focus starts on Keep editing. Returning to the editor restores the prior control only when the confirmation still owned focus; deliberate outside focus or blur is preserved. Discarding a study switch resets stale recode settings for the new study.

A clean initial/selected-study context, verified saved history and an acknowledged saved prepared copy do not require a discard question. Later edits and failed saves remain protected. An undone redo branch is still unsaved even after a copy of only the active steps is saved. A pending check/save must be canceled before closing or switching; late canceled results keep their existing epoch/signal handling. No raw rows, source/analysis/history metadata or workspace recovery copy is removed by this guard.

While work is unsaved or processing, a beforeunload handler requests the browser's normal warning. Browsers decide whether to display that prompt; it is not autosave, durable crash recovery, a guarantee against forced termination, or persistence of unfinished recipes after confirmed discard. Removing the whole parent by an unrelated route remains a separate acceptance boundary. Existing separate-copy save/recovery remains authoritative.

Regression coverage includes close/Escape, study switching, editor fields, undo/redo, preview, successful/failed saves, verified loaded history, busy work, focus ownership and unload-handler state. Existing parent quota/global-retry tests now explicitly discard the editor before using global recovery; their original retained-copy/source assertions remain. A real-App1,000-row synthetic journey preserves the original workspace and published snapshot while canceling close/switch, deliberately discards only editor state, creates a separate reviewed lowercase copy, then reloads its verified history through same-process remount. No native browser/unload/assistive-technology/touch or real crash claim is made. Original goal11remains partial. Source stays isolated from the stale main index; no production build retry, publication, merge or deployment.

A study-switch destination is checked again before discard. If it is missing or ambiguous, the editor returns with the existing history and preview intact, rather than clearing work for an invalid destination. Tests cover both changes while confirmation is open.

## Recipe acknowledgement does not save editor drafts

The saved recipe and next-step editor have separate clean baselines. A successful copy save acknowledges only the recipe it persisted. A configured but unapplied field/operation/recode selection/target remains unsaved, even after previewing and saving current history. Applying a previewed step consumes only the choices represented by that step; an inactive recode target is not silently marked saved by applying a non-recode operation. Returning editor choices to their last consumed state can become clean without resaving the recipe.

The editor explicitly explains that saving a copy saves applied history only. Regressions reproduce successful-save acknowledgement with an additional unapplied recode and protect both close and study switching, including selected codes and target text. Further cases cover returning choices to their consumed baseline and preserving an inactive recode target. These checks do not add persistence for unfinished editor state.

The1,000-row actual-App journey also configures an unapplied recode before saving current history. It verifies that the persisted copy contains only the applied lowercase step, then checks the unsaved selected code/target survive successful save and Keep editing. Explicit discard closes only that editor state; reopened persisted history is clean and unchanged.

## Hold in-app route transitions before preparation unmounts

While this mounted tool has unsaved work, hash and browser-history events are held in the window capture phase before the existing App/Builder route listeners can unmount it. The current component remains mounted with its recipe and editor state. A duplicate event for the same pending destination does not reset the decision or focus. A new destination replaces the pending target. Same-editor route aliases/notifications do not cause a false leave question or rebind the mounted editor.

Keep editing returns to the retained report address using a normal history return entry; it does not overwrite older entries or reconstruct/rewind the browser history stack. As with normal pushState navigation, a return entry can replace the browser's forward branch. Explicit Discard and leave releases only the current, checked destination to the existing route flow. A destination changed without a route event refuses stale leave consent. If the browser refuses the return history operation, the decision and work remain mounted with an explanation. Interrupted preparation checks/saves are aborted and their late acknowledgements ignored; already completed workspace/recovery copies are not rolled back or removed.

This guards the application's hash/popstate route lifecycle, not external documents, forced reloads, crashes, arbitrary parent unmounts or third-party capture routers. Beforeunload remains browser-controlled; unfinished recipes are not automatically persisted. Real-App tests use actual jsdom location/history operations, including Back, to Home, another report and a local published viewer. Native browser Back/Forward/address-bar timing, assistive technology and touch acceptance remain open; no production build or blocked native operation is retried.

## Explicit recovery checkpoints for unfinished work

Save recovery checkpoint retains a separate versioned browser-storage record containing the original-study identity and full source-metadata digest, prepared-copy title, all applied and undone history, Undo cursor, selected field/operation/codes and target text. It is an explicit action, not automatic keystroke saving. A checkpoint does not create a prepared study, clear unsaved-editor protection, persist a preview's response rows, or carry forward review approval. An un-applied preview must be rebuilt from its retained editor choices. The editor's existing preview remains visible after checkpoint creation.

Reopen preparation in the same report, choose its checkpoint and Restore recovery checkpoint. Restoration is disabled while the current editor is dirty; first close/discard that editor explicitly and reopen. Source values and all source metadata must match the frozen digest (property ordering alone does not matter), with exactly one complete local original source available. Restoration binds the recovered recipe to that original, rather than rebinding a prepared revision under a reused ID. It restores history, redo and editor choices as unsaved work; preview and review are required again before the ordinary separate-copy writer can create a study. No study, report, snapshot or normal workspace-save key is replaced by checkpoint save/restore.

Each explicit checkpoint uses a new cryptographic UUID key. Prior copies are never overwritten, evicted or automatically deleted, including after successful study creation. The UI offers Refresh recovery checkpoints to inspect records saved by another tab. Up to eight records per report are allowed; there is currently no in-app deletion/export of these records. Concurrent tabs can exceed the count limit because this is not an atomic multi-tab transaction, but distinct generated identities do not intentionally replace older records. Browser quota/denial or an unconfirmed readback never reports a successful checkpoint. An unconfirmed write might nevertheless have retained a record; refresh before retrying.

Records are limited to 65,536 UTF-16 code units (at most 128 KiB of payload text); larger recipes refuse without truncation. Source checking is bounded to 20 MiB of serialized source metadata/values, but freezing and serialization still allocate in memory before the size check. Storage inventory inspects at most 20,000 keys and at most 20 matching records. Damaged, unknown-version and oversized stored records are retained and withheld from restoration. Missing/changed source, changed record, cancellation, unmount and stale operation ownership fail closed without consuming a checkpoint. These bounds are not proof of total browser memory or performance limits.

Checkpoint codes and editor text may contain sensitive category/author-entered content; they are not anonymized, encrypted or copied into a portable workspace backup. Clearing browser storage, private-browsing cleanup, device loss or eviction can remove them. This is browser-local recoverability of an explicitly acknowledged checkpoint, not guaranteed power-loss durability, crash-atomic saving, cloud recovery or recovery of later uncheckpointed edits. Existing native/browser/assistive-technology/build acceptance gaps remain. Goal 11 remains partial pending review and its broader acceptance.

Successful restoration also clears an already-saved preview and its review approval when restoring into a clean existing editor. The recovered recipe cannot reuse an unrelated preview: another preview and explicit review are required. Checkpoint creation itself leaves the current preview and its approval intact because it does not replace the editor.

Changing the checkpoint selection during source checking cancels that restore and requires an explicit Restore action for the new selection. Each restore captures its selected key and operation ownership and checks both before applying editor state. A late canceled result cannot restore A beneath a selector showing B, or clear the busy state of a newer restore. Existing checkpoint bytes and study/workspace data are retained.

## Portable checkpoint backup management

Download selected checkpoint requests a tagged JSON backup of a valid selected checkpoint. Codes and editor text are stored and downloaded **unencrypted**; the UI explicitly says to keep files private. No complete study table is included, so keep an original workspace/study backup separately. These controls do not delete browser checkpoints or treat a requested download as proof that the user received it.

Choose a checkpoint backup file to inspect its title, original time, required source ID, history/cursor and full recipe/editor text before import. Reading and inspection never import automatically or replace the current editor. The reader accepts at most 512 KiB, validates UTF-8 and the tagged versioned JSON format, and refuses unsupported/oversized records. Text is rendered in a readonly text area; it is not executed. New file selection, explicit cancel, report changes and unmount invalidate old reader callbacks. Completion/cancel returns focus from the Cancel control only if that control still owns focus.

Import inspected checkpoint adds a separate browser checkpoint with a new cryptographic identity while retaining the recipe, source fingerprint, original timestamp and editor choices. The file and earlier browser records remain intact. An exact existing record or an equivalent already-imported copy is reused without another write or slot. A file whose original identity already exists with different bytes refuses rather than overwriting it. Distinct imports append unique keys so interleaved imports cannot intentionally replace one another. Unknown/unreadable records count toward the existing eight-checkpoint limit and are never evicted to make room. As with existing checkpoint creation, the count check is not an atomic multi-tab transaction; simultaneous operations can exceed that advisory count while retaining copies. The limit is not raised by this feature.

Only the original report identity is supported; the file is not silently rebound to another report or source. Import is separate from restoration: a missing or changed original study still prevents restore. Importing while another editor has unfinished work leaves that editor unchanged; discard it explicitly before restoring. No ordinary workspace, source study, report page or snapshot is written by file inspection/import. After a failed acknowledgement, a copy may already exist; retry reuses matching content without duplicating it.

Native OS chooser/download receipt, browser matrix, real quota/crash, cross-device browser storage and accessibility acceptance remain open. Component tests use actual jsdom FileReader/File objects; a same-process App journey inspects/imports, preserves a different unfinished editor, then reopens/restores and saves a separate prepared study through the actual writer. This does not prove a physical download or browser process restart. There is still no in-app deletion of checkpoints, and portable files are separate from the ordinary workspace backup format.

The file input captures the chosen File and immediately clears its native selection before inspecting. This permits choosing the same unchanged file again after cancellation or a read error, rather than relying on a browser to emit change for an unchanged filename. The captured File remains valid even though clearing the input also clears its FileList. Retry remains explicit and does not import automatically. Component regressions model the same-filename picker boundary and cover cancellation/error retry, capture-before-clear and stale first-reader results; native chooser behavior remains unverified.
