# Preserve distinct imported category codes

The earlier label lookup rounded a raw code with Number before applying a canonical numeric label. It could merge `1e-9999` into a labeled `0`, or `9007199254740993` into a labeled `9007199254740992`. Both analysis counts and category audiences used this behavior. Original stored rows remained intact, but the resulting membership and counts were incorrect.

Analysis and audience matching now share one category-code function. An exact own dictionary key still takes precedence. Otherwise a proposed canonical numeric label applies only when the source and label have exactly equal decimal spellings after sign, coefficient and exponent normalization. `01`, `1.0`, `1e0` and `10e-1` still map to a declared `1`; signed or exponent-form genuine zeros still map to declared `0`. Nonzero underflow and precision-rounded values remain distinct codes. This is exact decimal-code equality, not a claim that a decimal value is exactly representable in binary64.

Compatibility is intentionally narrower for unsafe or nondecimal aliases: hexadecimal, binary and octal spellings no longer acquire decimal labels through Number conversion. They remain usable literal categories, and explicit own labels still work. No currency/percentage/comma parsing was added to categories. Existing blank handling, whitespace trimming, partial label dictionaries, exact-key priority and own-property checks remain. Normalization uses strings and bounded exponent arithmetic, without constructing powers of ten or large integer values.

The common interpretation reaches grouping, breakout columns, filter choices/matching, category profile counts and audience choices/membership. Python Decimal supplies 44 exact reference comparisons: 26 legitimate aliases and 18 distinct codes. Tests cover own/inherited/prototype-like keys, large exponent strings, signed zero, underflow, precision boundaries, blank/excluded respondents, profile and worker-model parity, preserved label dictionaries and raw rows. Existing numeric parsing/summation are unchanged.

The actual App regression starts with a cached result representing the former merge in a synthetic 1,000-row, 30-field study. It preserves that cache until the user previews and approves a fresh calculation. The corrected result contains 499 observed-zero responses, 500 code-2 responses and one literal `1e-9999` response, with base 1,000. It checks a sealed execution receipt, save, Undo, Redo and cold reopen while preserving all original imported rows, labels, layout and report elements. Historical results are not automatically rewritten or retroactively certified.

App checks use jsdom with dialog/scroll shims. Production worker execution in Node, where checked, is not native browser scheduling or performance acceptance. Live backend, native browser/assistive technology, native Office and OS downloads remain unverified. This correction closes a bounded alias defect; it does not certify every categorical workflow or complete another roadmap goal. Publication, merge, deployment and environment security changes are excluded.
