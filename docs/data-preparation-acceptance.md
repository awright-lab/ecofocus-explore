# Reversible data preparation — original goal 11 candidate

Original goal: visual history for cleaning, recoding and combining categories, with previews and Undo. The complete local workflow is **Find a tool → Analyze → Clean and recode a study copy**. Independent original-scope review is pending.

Choose a complete original local-file study, then a text/categorical field. Preview trimming, lowercase/uppercase, repeated-whitespace cleanup or an explicit many-to-one raw-code recode. Exact string matching is case-sensitive; there is no numeric coercion. Blank can be selected deliberately or used as a target to make values missing. Code choices reflect applied steps. Changed codes and targets that gain merged responses lose their old value labels, preventing old meanings from being assigned to new combined categories.

Every step shows its operation, field and code mapping in an ordered history. Preview displays retained row count, per-step change counts, affected rows and the first 25 final differences, with quoted original/prepared values. A preview must be applied before it enters history. Undo/Redo replays prefixes from the unchanged original; a new applied step replaces only the undone branch. The user explicitly reviews before creating a separate prepared study. All original rows and columns remain; only chosen copy cells change. Existing studies, report analyses and audiences are not rebound.

Prepared copies have new study/import identities and a versioned recipe, with original ID/import and a SHA-256 content fingerprint. The fingerprint detects changes; it is not source authentication. Saved history is reopened only after fingerprint checking and replaying its exact output. Undoing a reopened recipe can produce another separate revision; earlier copies and their analyses remain unchanged. Source removal is blocked while preparation histories use it. Snapshots referring to a prepared study retain its original source too. Damaged saved recipes fail validation before normalization; uncertain saved data is preserved.

Creation uses the actual browser workspace writer. Source, route, edit generation, cancellation and workspace ownership are checked before adding a copy. Failed saves retain the candidate and ordinary pending-work recovery; success is reported only after an acknowledged save. Same-copy retries tolerate storage notes/status but require identical analytical content, preserving the existing copy. There is no transactional-storage or crash-recovery activation.

Review correction: the parent save callback now uses the full additive workspace as pending recovery. Passing the pre-copy workspace could let the global Retry action save only that older copy and clear its warning while the prepared copy remained only in mounted editor state. A regression mounts the actual App and Builder, drives the real preparation dialog, injects a storage quota failure, inspects the real session's pending studies, invokes the real global Retry button and reads the stored workspace again. It fails on the old callback and passes on the correction; neither onSave nor persistence/session is mocked. DOM-only dialog/geometry APIs are shimmed for jsdom. This proves the tested recovery handoff, not actual browser quota capacity, simultaneous-tab atomicity or crash durability.

## Limits

Complete local-file studies: 1–50,000 source rows, at most 200 fields, 20 MiB of fingerprinted source values/metadata, 30 steps. Only text/categorical columns; no numeric/date derivations, row deletion, remote execution, arbitrary code or weights/inference. Up to 100 exact codes per recode, with the first 500 distinct codes available in the visual picker. Unsaved history is session-only; saved history requires its unchanged original to replay. Copies consume additional storage. Output metadata labels are conservative rather than inferred; review prepared categories before analysis. No source-authentication, cloud synchronization, live Snowflake, native Office or OS-download acceptance is implied.
