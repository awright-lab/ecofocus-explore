# Preserve recovered studies through save acknowledgement

An import that finishes after leaving its screen remains in the shared recovery queue. Previously **Add recovered studies** upserted every queued record, so a provider reusing an existing study ID could replace that study's answers without a separate source review. It also cleared the whole queue immediately after a synchronous write attempt.

Recovery is now additive. Different copies that share an ID remain separately queued; inconsistent rows, labels, notes, import versions or other meaningful metadata prevent a write. Existing report/snapshot references and prepared-copy dependencies reserve missing study identities, so recovery cannot silently bind them to a new source. Matching existing copies are reused without replacing their objects. The technical storage note is ignored for comparison, and automatically selected preview rows are redundant only when their complete values are present in the retained rows. Distinct partial preview data is preserved and compared.

The recovery action captures a bounded plain-JSON copy, updates the current workspace optimistically and awaits the specific `saveAsync` acknowledgement. Its queue entries remain until that acknowledgement, with unload protection and a backup action. Repeat clicks do not submit another write. Newer arrivals have distinct lifetime tokens and cannot be cleared by the older save. Changed queued data, altered candidate rows, navigation, unmount, a different workspace or a newer UI revision retain recovery copies. A rejected response does not overwrite another operation's newer shared pending save.

A failed write leaves both the existing saved version and the recovery copy available. **Add recovered studies** retries the checked addition. A generic **Retry saving** can save the combined workspace, but does not itself acknowledge the separate import queue; running **Add recovered studies** again checks the identical saved study without duplicating or replacing it. The success message follows acknowledgement. Keyboard focus stays on the busy action, then moves to its persistent status only when that removed action still owned focus.

Serialization checks run before cloning and comparison, with a combined 16 MiB JSON-character, two-million-value and 96-level budget. Sparse arrays, accessors, custom serialization hooks, hidden/symbol metadata and nonfinite values are refused. These limits are availability safeguards, not a total browser-memory or responsiveness guarantee. A refused source remains queued. Unknown metadata that normalization would discard is also refused instead of being silently stripped. Netlify copies with browser rows or more than 80 fields, and partial preview-only information beyond the current codec's 25-row preview, remain available for backup/review rather than being silently compacted. No connected service is queried or changed.

Regression coverage includes a real App with a 1,000-row/30-field saved source and an actual analytical result: the pre-fix action replaces its data under the same ID; the corrected action performs no workspace write and preserves the entire saved source/report. Actual writer quota failure, explicit retry, cold App remount and a versioned backup preserve all 30,000 source cells. Model, queue and component cases cover identity conflicts, missing dependencies, immutable captures, late responses, newer arrivals, source/candidate mutation, focus ownership, serialization refusal and existing navigation-recovery behavior. Tests use fabricated data and simulated browser facilities; they do not establish native Worker/chooser/download, actual browser quota, multi-tab atomicity or crash durability.

This is a safety prerequisite for asynchronous storage integration. The active writer remains the existing localStorage adapter. Transactional workspace activation, durable startup recovery and backup restoration remain gated; no original goal is newly counted complete by this batch. No merge, production deployment, database, credential, permission, billing or security-setting change is included.

Independent review identified two defensive API boundaries beyond the normal decoded App import path. Recovery now refuses any own encoded `rowStorage` record before decoding, retaining unknown codec metadata in the queue/backup instead of stripping it. If an identical source exists only inside a report, recovery promotes a validated copy to workspace-level storage before acknowledging it; the active writer clears embedded draft data. Original embedded objects and snapshots are not changed. Regression controls reproduced both pre-fix boundary behaviors; these are API-level cases, not established native user-data losses.
