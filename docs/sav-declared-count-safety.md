# SAV declared case-count safety

Classic SAV imports with a positive declared case count now refuse surplus physical data instead of accepting only the declared prefix. Uncompressed data must match the declared number of complete cases. Standard bytecode parsing checks for another physical value after the declared cases, while retaining supported no-op padding and optional end markers. The existing recognized-integrity path prevents fallback or supplied metadata from accepting the refused input.

A preserved original-module capture shows three physical cases (1,10), (2,20), (3,30) but a header declaring one. The old importer saved only (1,10) and reported mean 10/base1. An independent Python struct/Fraction reference verifies all three coded cases and whole-stream mean20. The new importer refuses the inconsistency; it does not decide which case count the source author intended. An explicitly repaired source imports separately with three rows and mean20/base3.

The [GNU PSPP developer's system-file reference](https://pspp.benpfaff.org/manual/system-file.html) documents case counts, standard compressed no-op codes and optional end markers. This candidate covers classic system files, not the separate SPSS/PC+ data format. Known exact counts, unknown negative counts, clean EOF without an end marker, zero-control padding, raw compressed values and 1,000-row inputs remain supported. Surplus system-missing and space-value slots are detected too. An explicit compressed end marker still ends the stream; bytes after that marker are outside this check.

Historical studies are not migrated. Tests preserve old imported rows, cached results, reports and snapshots byte-exact on load/resave, and retain them when an explicitly repaired study is added. Actual App/Home jsdom tests cover failure without writes, repaired import, actual numeric profile/query and cold reopen. Handler tests inspect original upload bytes and complete batched row payloads using mocked dependencies. All new inputs are synthetic.

Scope is positive declared counts in currently supported classic raw/bytecode paths. Existing zero-count behavior, extended64bit counts, nominal-width handling, missing-value semantics, full trailing-file validation, unsupported compression and native-format interoperability remain separate work. Native browser/SPSS/Office/downloads, assistive technology, live backend and Snowflake are unverified. No forty-goal completion is added.
