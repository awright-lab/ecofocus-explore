# Open-ended response coding — original goal 24 candidate

Original goal: organize comments into editable themes, connect them to supporting responses, and review coding disagreements. Independent acceptance remains pending.

**Find a tool → Analyze → Code open-ended responses** adds a manual, source-bound coding project saved within the current report. It supports complete original local-file imports with 1–50,000 rows; selected identifiers/comments/metadata must fit within 20 MiB. No respondent data is modified. Remote, partial and prepared studies are explicitly unsupported.

## Complete workflow

1. Name a project and two distinct manual coding passes. Choose the original study, a nonblank globally unique respondent-ID field and a separate comment field. Verify exact selected source values and metadata before beginning or resuming coding. Blank comments remain separately reported and are not coded.
2. Define up to 100 named themes with editable inclusion/exclusion guidance. Changes retain all prior assignments, advance the theme revision and mark older coding as needing review. Adding a theme likewise requires review of older assignments against the expanded definition set.
3. Search all original comment text/IDs, page through 20 responses at a time, and select a source row. Exact comment text remains visible; the list uses a preview for long responses. Assign multiple themes or explicitly mark reviewed with no themes. Empty unchecked boxes alone do not imply a completed review.
4. Compare the two passes. Unreviewed, one-pass, old-theme-review, agreement, disagreement and resolved states are distinct. Review disagreements alongside the original response and both recorded theme sets. A final decision requires both passes to reference the current theme revision and a nonblank reason. Changing either pass clears its old resolution.
5. Open a theme's supporting comments. Counts separately describe each current-revision pass and agreed/resolved decisions. Themes can overlap; totals are not exclusive population percentages. Supporting-comment filters can include historical/disputed assignments, explicitly labeled by their current review state.
6. **Apply coding to report** creates an ordinary undoable report edit. It does not claim the browser save succeeded: the report toolbar supplies that status, and actual failed saves use the existing pending recovery/Retry controls. Up to ten coding projects may be saved per report. Closing unapplied coding requires an explicit discard decision; the existing saved coding and comments are retained.
7. Reopen saved coding after verifying its exact source version. SHA-256 binds selected raw IDs/comments, question/ID field metadata, study/import identity and source shape. Changed source text, metadata or import identity cannot silently inherit old coding. A concurrently changed saved project cannot be overwritten by an older dialog. Source-study removal and snapshot capture include coding dependencies.

Two named passes are **manual records**, not authenticated or independently blinded reviewers. No AI-generated themes, agreement coefficients, significance tests, automatic coding or paid services are involved. No global theme deletion or silent recoding is performed. Source versions authenticate consistency within the local report, not the truth or origin of a respondent's statements.

## Independent review correction — unrecorded editor drafts

Independent review found that theme-name/guidance edits and resolution reasons or selections were not protected when the last recorded project version had already been applied. They are now tracked separately from recorded coding, retained while navigating between themes, responses or passes, and included in Close/Escape and beforeunload protection. Draft shortcuts reopen their editors. Recorded coding cannot be applied while editor drafts remain; users must record them, discard one editor draft, or explicitly discard all unrecorded drafts. Reverting a field exactly to its recorded value removes its draft state without editing the project. The warning stays focused and visible, and existing applied coding is preserved.

The reviewer's resolution-draft regression fails against the earlier candidate and passes with the correction. Final integration: **2,180 tests passed, two existing skips**, TypeScript and production build passed. Native acceptance resumed an already-applied 1,000 × 30 project, typed unrecorded resolution reasoning and theme guidance, verified Close → Keep editing and cross-editor navigation retain both, then explicitly discarded them. The entire **520,021-character** captured applied studies/pages/codebooks/audiences/library/snapshots content remained byte-identical after discard and cold reload. Native browser unload prompting was not invoked; its actual event-handler protection is verified in component tests. Original-goal acceptance remains pending independent re-review.

## Limits

This is local manual qualitative coding. Remote identities, collaboration, inter-rater reliability statistics, AI theme discovery, exports, weighted prevalence/inference, prepared-study linkage and cryptographic source authentication are outside the candidate's scope. There is no new transactional workspace writer or crash-durability claim; current local save/recovery limits still apply. Verification performs bounded main-thread projection work and asynchronous fingerprinting/counting; it is not a general background import engine. Theme edits retain assignments but do not provide a permanent audit history beyond ordinary report editing/history. No Office rendering, OS downloads, merge or deployment was attempted for this batch.
